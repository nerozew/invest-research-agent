# 产品需求文档（PRD）

## 1. 文档信息

- 产品名称：Agent 驱动的自动化投研系统
- 当前阶段：MVP 设计
- 目标用户：证券研究员、投资分析师、希望学习 Agent 工程化的开发者
- 首期市场范围：美国上市公司与 SEC EDGAR 公开数据
- 报告语言：中文为主，可配置英文

## 2. 背景与问题

传统公司研究需要分析师在搜索引擎、SEC、财报文件和本地表格之间反复切换。大量时间消耗在查找材料、复制数字、统一口径、计算指标、整理引用和排版，而不是判断数据含义。

本产品把这类可重复工作编排成可追踪的 Multi-Agent 工作流。系统不能替代分析师判断；它的价值是更快地产生一份来源清晰、可复核的研究初稿。

## 3. 产品目标

### 3.1 业务目标

- 将“收集资料到产出初稿”的人工耗时显著降低。
- 减少复制错误、公式错误和来源丢失。
- 让每一个事实、数值和结论都能回溯到数据源或计算公式。
- 形成可在本地完整复现的 Multi-Agent、复杂工作流、可靠性与容器化部署项目。

### 3.2 技术目标

- 使用 CrewAI 实现三个职责明确的 Agent 和顺序工作流。
- 集成不少于 5 个可真实使用的工具。
- 每一步产生 Pydantic 结构化输出和持久化工件。
- 对可恢复故障实现超时、重试、幂等、降级和断点续跑。
- 在定义清楚的测试集上达到有效任务成功率 > 95%。

### 3.3 非目标

- 不提供买入、卖出、目标价或个性化投资建议。
- MVP 不覆盖非 SEC 公司、私营公司、基金和加密资产。
- MVP 不做实时行情、自动交易、组合管理和券商账户连接。
- MVP 不用 LLM 直接完成算术或把未经验证的搜索摘要当成事实。
- MVP 不追求复杂前端；先提供 CLI、FastAPI 和简单任务状态查询。
- 当前项目不包含 Azure 或其他付费云平台部署；云部署仅作为项目完成后的可选升级方案。

## 4. 用户角色与核心场景

### 4.1 研究分析师

输入公司名称或 ticker，选择数据截止日期和报告语言，得到一份带引用的报告初稿，并可查看每个步骤的中间结果。

### 4.2 系统维护者

查看失败步骤、工具调用日志、重试次数、Token 消耗和报告质量检查结果；修复问题后从失败步骤恢复任务。

### 4.3 学习者/开发者

按小任务实现项目；每个任务都有可验证产物、测试和知识总结，不依赖 AI 一次性生成整套代码。

## 5. 端到端用户故事

> 作为分析师，我输入 `Microsoft` 或 `MSFT`，选择截至某日生成中文报告。系统识别公司与 CIK，获取最新 10-K、最近季度数据和相关新闻，解析文件并计算财务指标，随后生成带引用的 Markdown/PDF 初稿。我可以查看执行进度、中间 JSON、原始文件、计算公式和失败原因。

## 6. 功能需求

| 编号 | 功能 | MVP 验收条件 | 优先级 |
|---|---|---|---|
| FR-001 | 创建研究任务 | 接受公司名或 ticker、`as_of_date`、语言；返回唯一 `job_id` | P0 |
| FR-002 | 公司身份解析 | 返回 ticker、10 位 CIK、法定名称、交易所；歧义时返回候选，不静默猜测 | P0 |
| FR-003 | SEC 申报检索 | 获取截至指定日期可用的最新 10-K 和最近 10-Q 元数据及原文 URL | P0 |
| FR-004 | XBRL 财务事实 | 获取并规范化 SEC Company Facts；保留 taxonomy、concept、单位、期间和表单类型 | P0 |
| FR-005 | Web 信息检索 | 通过 Google 结果提供商检索公司、行业、风险和近期事件；保存标题、URL、发布时间和访问时间 | P0 |
| FR-006 | 文档下载与解析 | 优先解析 SEC HTML，支持 PDF；失败时按预设顺序降级；保存原始文件和规范化文本 | P0 |
| FR-007 | 财务指标计算 | 用 Decimal/确定性代码计算增长率、利润率、偿债与现金流指标；记录公式、输入和状态 | P0 |
| FR-008 | Multi-Agent 协作 | 信息搜集 Agent → 财报分析 Agent → 报告撰写 Agent 严格顺序执行 | P0 |
| FR-009 | 中间产出 | 每个步骤写入数据库并生成带 checksum 的 JSON/Markdown 工件 | P0 |
| FR-010 | 报告生成 | 生成公司概览、关键事件、财务分析、风险、催化因素、限制与来源章节 | P0 |
| FR-011 | 引用追踪 | 重要事实和外部数值包含可点击来源；派生指标链接到公式和原始事实 | P0 |
| FR-012 | 质量门禁 | 报告发布前完成 schema、引用、数字一致性和必需章节检查 | P0 |
| FR-013 | 状态查询 | 可查询任务状态、当前步骤、步骤耗时、重试次数、错误码和工件清单 | P0 |
| FR-014 | 恢复执行 | 对同一 `job_id` 重跑时跳过已验证成功的步骤，从首个未完成步骤继续 | P1 |
| FR-015 | 报告导出 | MVP 输出 Markdown；第二阶段增加 PDF | P1 |
| FR-016 | 任务取消 | 可请求取消，当前安全点完成后停止，不留下“运行中”的脏状态 | P2 |

## 7. 报告结构

1. 封面信息：公司、ticker、CIK、数据截止日、生成时间、声明。
2. 执行摘要：只总结报告内已经有证据支持的内容。
3. 公司与业务概览。
4. 近期重要事件与行业背景。
5. 财务表现：收入、利润率、现金流、资产负债与趋势。
6. 关键指标表：值、期间、同比/环比、公式与来源。
7. 风险因素与潜在催化因素，明确区分事实与分析。
8. 数据限制和未解决的矛盾。
9. 来源清单与引用。

## 7.5 受控反思与修订闭环（Phase 3.5 补充需求）

质量问题由确定性质量门禁（FR-012）识别，并按受控方式闭环处理，不增加第四个审核 Agent：

- **无问题** → 直接发布。
- **仅非关键警告** → 以 `partial` 发布（带警告记录）。
- **可修复问题（章节/表述/免责声明）** → 由 Flow 触发 **Writer 定向修订（≤1 次）**，仅修改被指出的问题，不新增上游不存在的事实，不改动 FinancialFact / MetricResult。
- **缺少关键证据** → 生成结构化**补证请求**，由 Research 补充一次（≤1 次）后重新 Analysis → Writer → 质量门禁。
- **数字篡改 / 关键引用仍缺失 / 不可修复 / 次数耗尽** → 拒绝（rejected/partial）。

约束：反思次数硬上限（修订≤1、补证≤1）、不允许无限循环、所有循环由 Flow 控制（Agent 不互相调用）、每次报告草稿与质量报告及修订/补证原因均保留以供审计。

## 8. 关键指标与公式范围

MVP 至少实现以下指标；分母为零、口径或期间不可比时返回 `not_computable`，禁止臆造数值。

| 指标 | 公式 |
|---|---|
| 收入增长率 | `(本期收入 - 上期可比收入) / abs(上期可比收入)` |
| 毛利率 | `毛利润 / 收入` |
| 营业利润率 | `营业利润 / 收入` |
| 净利率 | `净利润 / 收入` |
| 流动比率 | `流动资产 / 流动负债` |
| 资产负债率 | `总负债 / 总资产` |
| 经营现金流率 | `经营活动现金流 / 收入` |
| 自由现金流 | `经营活动现金流 - 资本性支出` |
| ROA | `净利润 / 平均总资产` |
| ROE | `净利润 / 平均股东权益` |

公式必须带版本，例如 `financial_metrics_v1`；计算输入必须保存 concept、期间、单位和来源。

## 9. 非功能需求

### 9.1 可靠性

- 有效任务成功率：100 次受控运行中至少 96 次达到“成功”定义，即严格大于 95%。
- 所有外部 I/O 必须设置连接和读取超时。
- 对 408、429、可恢复的 5xx 与网络异常使用指数退避加随机抖动。
- 不对无效输入、认证失败、schema 永久不兼容等错误盲目重试。
- 每个步骤具备幂等键，可安全重放。

### 9.2 性能与成本

- MVP 目标：单公司报告 P95 完成时间不超过 15 分钟，不含第三方长期故障。
- Web 和 SEC 结果按内容 hash 缓存；重复任务尽量复用原始文档和解析结果。
- 保存每个任务的 LLM Token、API 请求次数和估算成本。

### 9.3 数据质量

- 100% 的报告内关键数值可回溯到原始事实或明确公式。
- 必需章节完整率 100%。
- 引用 URL 可解析率 ≥ 99%，外部站点事后下线不计为生成时失败。
- 不同来源冲突时必须记录冲突，不由 Agent 静默选择。

### 9.4 安全

- API key 只从环境变量或密钥服务读取，不进入代码、提示词、日志和数据库。
- 工具日志中的认证头、Cookie、个人信息和大段原文必须脱敏。
- 文件名由系统生成，禁止使用未经清理的公司名直接拼接路径。
- 对下载大小、媒体类型、重定向次数和 URL scheme 设限，降低 SSRF 与恶意文件风险。

### 9.5 可观测性

- JSON 结构化日志统一包含 `job_id`、`step_name`、`tool_name`、`attempt` 和 `trace_id`。
- 记录工作流成功率、步骤成功率、延迟、重试、缓存命中、工具错误、LLM Token 和质量门禁失败。
- 本地使用 Prometheus 收集指标、Grafana 展示仪表盘，并使用 OpenTelemetry 记录调用链。

## 10. 状态定义

- Job：`pending`、`running`、`succeeded`、`partial`、`failed`、`cancelled`。
- Step：`pending`、`running`、`succeeded`、`failed_retryable`、`failed_terminal`、`skipped`。
- `partial` 表示报告已生成，但非关键来源缺失或质量门禁只允许“带警告发布”。

## 11. “成功率 > 95%”的可验证定义

### 11.1 有效输入

公司能唯一映射到 SEC CIK，目标申报在 `as_of_date` 前存在，并且请求参数通过校验。无效输入是产品校验结果，不计入工作流失败率，但必须单独统计。

### 11.2 成功任务

同时满足以下条件：

- 所有 P0 步骤状态为 `succeeded`。
- 产出最终报告、fact pack、metrics、quality report 和 manifest。
- 最终报告通过 schema、必需章节、数字一致性和引用门禁。
- 没有未处理异常或残留 `running` 状态。

### 11.3 基准集

- 选择 20 家不同行业、不同规模、财年日期不同的 SEC 公司。
- 每家公司运行 5 个预先固定的测试场景，共 100 次。
- 固定配置、模型版本、时间窗口和网络条件，保存每次 run manifest。
- `成功率 = succeeded / 有效任务总数 × 100%`。

## 12. 效率提升的测量方法

不能在测量前写“提升 XX%”。邀请至少一名使用者对 10 家公司执行同一报告模板：

- `人工基线时间`：资料搜集 + 计算 + 初稿。
- `系统辅助时间`：自动运行等待时间不计人工工时；计入输入、复核和修订的人工作业时间。
- `人工效率提升 = (人工基线工时 - 系统辅助人工工时) / 人工基线工时 × 100%`。
- 同时记录报告修订率、数字错误数和引用缺失数，避免只优化速度。

## 13. 发布验收

- 使用 3 家固定公司完成端到端演示且可以复现。
- 断网、SEC 429、搜索超时、LLM 无效 JSON、PDF 解析失败等故障测试通过。
- 数据库迁移可在空库执行，也可回滚最近一次迁移。
- `.env.example` 完整但不包含真实密钥。
- README 包含本地启动、测试、演示和已知限制。
- 100 次基准完成前，简历中只写“设计目标 >95%”，不得写成已达到。
