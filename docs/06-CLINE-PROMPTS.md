# Cline + DeepSeek 提示词手册

## 1. 先纠正两个名称

你描述的工具大概率是 VS Code 扩展 **Cline**，模型是 **DeepSeek**。Cline 负责读取/修改项目、执行命令和维护上下文；DeepSeek 是它调用的模型。两者分工不同，所以提示词需要同时约束“如何做工程”和“每次做多大范围”。

## 2. 最重要的用法

不要把“请帮我做完整投研系统”一次性交给 AI。对这个项目使用三层上下文：

1. **长期规则**：`.clinerules/`，每轮自动约束架构、测试和学习方式。
2. **项目事实**：`docs/01` 到 `docs/05`，描述需求、架构、数据库、可靠性和路线。
3. **当前任务**：一次只给一个任务 ID、明确验收、验证命令和停止条件。

一个高质量工程提示词包含：

```text
角色 + 已知上下文 + 单一目标 + 范围 + 禁止项
+ 明确产物 + 验收标准 + 验证方式 + 学习输出 + 停止条件
```

## 3. 第一次使用：项目总规划提示词（Plan 模式）

建议先在 Cline 输入 `/deep-planning`，再粘贴下面内容：

```text
你是这个项目的资深 Python/Agent 架构师，同时也是我的工程导师。

项目：Agent 驱动的自动化投研系统。
我的背景：我已经完成学习路线第 1、2、3、4、6 周，第 5 周监控与部署还没有系统学习。我希望边做边学。

请先完整阅读：
- README.md
- docs/01-PRD.md
- docs/02-ARCHITECTURE.md
- docs/03-DATABASE.md
- docs/04-WORKFLOW-RELIABILITY.md
- docs/05-DEVELOPMENT-ROADMAP.md
- .clinerules/ 下的规则

本轮只做规划，不修改文件、不安装依赖、不执行破坏性命令。

请：
1. 检查文档之间是否有冲突、遗漏或无法验收的指标。
2. 检查当前工作区真实状态，不假设代码已经存在。
3. 找出最早的未完成任务，并说明其前置条件。
4. 把该任务拆成不超过 7 个动作，每个动作说明涉及文件和验证方式。
5. 说明本任务不会做什么，防止范围扩张。
6. 给出本任务的测试策略、风险和回滚方法。
7. 用初学者能理解的语言解释我要学到的 3 个知识点。

输出格式：
A. 当前状态
B. 发现的问题/假设
C. 本次只建议执行的任务 ID
D. 实施计划
E. 验收命令
F. 学习目标
G. 等待我确认的问题

完成规划后停止，等我确认再进入 Act 模式。
```

## 4. 日常使用：单任务执行提示词（Act 模式）

把 `{TASK_ID}` 替换为路线中的一个 ID：

```text
请只执行 docs/05-DEVELOPMENT-ROADMAP.md 中的任务 {TASK_ID}。

开始前：
1. 阅读该任务、它的依赖和相关设计文档。
2. 检查当前文件与 git diff，保留已有修改。
3. 用 3–6 条列出本任务实施计划；如果任务超过 90 分钟学习粒度，先停止并建议拆分。

实施约束：
- 严格遵守 .clinerules/。
- 只修改完成该任务必需的文件；不要顺手实现下一任务。
- 不改变 PRD、ADR、数据库或公共接口，除非本任务明确要求。
- 先写或同步写测试；不得用删除测试、降低断言、跳过检查来制造通过。
- 外部 API 使用 mock/fixture；除非任务明确要求真实联网。
- 不写真实密钥，不在日志打印密钥。
- 发现不确定 API 时先查当前官方文档，不凭记忆编造。

验收：
- 执行该任务相关的最小测试、lint 和类型检查。
- 如命令失败，说明根因并在范围内修复；不能修复就保持任务未完成。
- 只有实际通过才把路线中该行任务 ID 从 `{TASK_ID}` 改为 `{TASK_ID} ✅`。

完成后按以下格式汇报并停止：
1. 目标
2. 修改文件
3. 关键实现
4. 实际验证命令与结果
5. 我需要掌握的 3 个知识点
6. 给我的一个检查问题（先不要给答案）
7. 已知限制/风险
8. 下一任务建议（只建议，不实施）
```

也可以直接在 Cline 中运行项目提供的 `/next-task.md` workflow，并附上任务 ID。

## 5. 第一轮可直接复制的提示词

当前目录只有设计文档时，第一步应该是 P00-01，而不是立刻生成代码：

```text
请只执行任务 P00-01：完整阅读项目设计文档，创建 docs/08-OPEN-QUESTIONS.md。

本轮只允许新增这一份文档，并在验收通过后给 P00-01 的任务 ID 添加 `✅`；不允许创建代码、初始化 Git、安装依赖或修改现有架构文档。

请把发现按以下类别记录：
- 文档间冲突
- 需要我决定的产品问题
- 可由代码/官方文档验证的技术问题
- 当前可以安全采用的默认假设
- 会影响 MVP 范围或数据正确性的风险

每一项写明：来源文档、为什么重要、推荐默认值、如果不决定会阻塞哪个任务。
最后列出 P00-02/P00-03 开始前必须解决的问题与可以延后决定的问题。

完成后给我 3 个最重要的问题并停止。
```

## 6. 单个工具的专用提示词模板

适用于 P02 系列：

```text
请只实现 {TOOL_NAME}，对应任务 {TASK_ID}。

工具契约：
- 输入模型：{INPUT_MODEL}
- 输出模型：{OUTPUT_MODEL}
- 允许调用：{UPSTREAM_API_OR_LIBRARY}
- 超时：{TIMEOUT}
- 可重试错误：{RETRYABLE_ERRORS}
- 永久错误：{TERMINAL_ERRORS}
- 幂等键：{IDEMPOTENCY_RULE}
- 日志必须脱敏：Authorization、API key、Cookie、完整正文

测试必须覆盖：
1. 正常响应。
2. 空结果或缺字段。
3. timeout/429/5xx 的错误映射。
4. 非法响应不能泄漏未处理异常。
5. 输入输出 Pydantic schema。
6. 该工具特有的边界条件：{BOUNDARIES}。

只实现 adapter 和测试，不接入 Agent、不修改 Flow。完成验证和学习卡片后停止。
```

## 7. Agent/Task 实现提示词模板

```text
请只实现 {AGENT_OR_TASK}，对应任务 {TASK_ID}。

请先从 docs/02-ARCHITECTURE.md 提取该 Agent 的：目标、允许工具、输出 schema 和禁止事项。不要重新发明角色。

要求：
- prompt 文件独立版本化，不把长 prompt 硬编码在业务类中。
- 明确 as_of_date，禁止使用截止日之后的信息。
- 工具白名单最小化；没有授权的工具不得暴露。
- 输出使用 output_pydantic，不仅仅是自然语言 JSON。
- 为 prompt 加 snapshot 测试，为 schema 加 fake LLM 测试。
- prompt 中区分事实、派生指标、分析、限制。
- 财务数字必须来自 FinancialFact/MetricResult，禁止模型自行计算。

本任务只完成单个 Agent/Task；不组合 Crew、不运行真实付费模型。完成后停止。
```

## 8. 调试提示词（先诊断，后修复）

当测试失败时，先在 Plan 模式使用：

```text
请诊断下面的失败，不要立刻修改代码：

任务 ID：{TASK_ID}
复现命令：{COMMAND}
错误输出：{ERROR}

请：
1. 亲自运行最小复现命令并定位第一个真实失败，不要只解释最后一行。
2. 列出最多 3 个根因假设，并用文件/日志/测试证据逐一排除。
3. 判断它是代码缺陷、测试缺陷、环境问题、上游契约变化还是设计冲突。
4. 给出最小修复范围、可能回归和验证命令。
5. 不要删除测试、扩大重试次数或捕获 Exception 来掩盖根因。

输出诊断结论后停止，等我确认再修复。
```

确认后切 Act：

```text
按刚才确认的根因执行最小修复。只修改已列出的文件；先补一个能复现问题的失败测试，再修复实现，并运行相关回归测试。完成后用“失败原因 → 修复机制 → 防回归测试”三句话总结并停止。
```

## 9. 代码审查提示词

```text
请只审查任务 {TASK_ID} 产生的 diff，不修改文件。

按优先级查找：
1. 财务数字或期间口径错误。
2. 状态机、事务、幂等和重试错误。
3. 密钥泄漏、SSRF、路径穿越和日志敏感信息。
4. 异步阻塞、连接未关闭、无限重试。
5. schema/数据库迁移不一致。
6. 测试缺口和“测试实际未验证”的假通过。

每个问题必须给：严重级别、文件与行、触发场景、影响、最小修复建议。没有证据的问题不要列。最后说明是否满足该任务验收；不要审查未改动的整个项目。
```

## 10. 学习复盘提示词

```text
不要改代码。请基于刚完成的任务 {TASK_ID} 给我做一次 10 分钟学习复盘：
1. 用类比解释核心概念。
2. 沿真实代码路径解释数据从输入到输出如何流动。
3. 指出一个常见错误以及我们的实现如何避免。
4. 给我 3 道由浅到深的问题，先等我回答。
5. 根据我的回答纠正理解，再让我用自己的话总结。
```

## 11. 架构变更提示词

任何数据库、框架、部署方式或基础设施变化先使用 Plan 模式：

```text
我考虑把 {CURRENT_DECISION} 改成 {PROPOSED_DECISION}。请不要改代码。

请基于 PRD 和 ADR 比较：MVP 价值、学习成本、可靠性、数据一致性、本地可复现性、测试复杂度、运行成本和回滚难度。给出保留现状、立即变更、延后到未来升级三个方案。明确哪些是假设，哪些能从当前代码或官方文档验证。

如果建议变更，请先草拟一份 ADR，列出受影响的任务和迁移顺序。等我确认后再改文档或代码。
```

## 12. 运行时三个 Agent 的 prompt 骨架

这些不是给 Cline 的开发提示词，而是将来写进 `src/.../prompts/` 的运行时模板。实现时应由 schema 和程序注入输入，不能靠自由文本拼接不可信内容。

### 12.1 信息搜集 Agent

```text
角色：你是审慎的公开信息研究员。
目标：围绕给定 CompanyIdentity 和 as_of_date 形成 ResearchPack。
权威顺序：SEC 原始申报 > 公司 IR 原文 > 高质量媒体 > 其他网页。
允许工具：CompanyResolver、GoogleSearch、SECSubmissions、SECCompanyFacts、FilingDownloader、ArtifactReader。

规则：
- 只使用 as_of_date 当日或之前已公开的信息。
- 每条事实保存 source_id、发布时间/申报日和 locator；没有访问原文不得声称已核实。
- 区分事实、来源的观点和你的摘要。
- 去重同一事件；不同来源冲突时记录 conflict，不自行消解。
- 不计算财务比率，不撰写最终投资结论。
- 输出必须符合 ResearchPack schema；缺失信息使用空列表/明确状态，不编造。
```

### 12.2 财报分析 Agent

```text
角色：你是重视会计口径和可复核性的财报分析员。
目标：基于 ResearchPack、FinancialFact 和 ParsedDocument 形成 FinancialAnalysisPack。
允许工具：ArtifactReader、FinancialFactQuery、FinancialCalculator。

规则：
- 只选择单位和期间可比的事实；说明季度、YTD、年度和 instant/duration 的差异。
- 所有算术必须调用 FinancialCalculator；禁止自行计算或从自然语言猜数。
- 每个指标保留 metric_id、formula_version、input fact ids 和期间。
- concept/单位/期间冲突时返回 ambiguous 或 not_computable，并解释原因。
- 区分数据事实、派生指标和解释性分析。
- 输出必须符合 FinancialAnalysisPack schema。
```

### 12.3 报告撰写 Agent

```text
角色：你是面向专业分析师的研究报告编辑。
目标：只使用上游 ResearchPack 和 FinancialAnalysisPack 生成结构化 ReportDraft。
允许工具：ArtifactReader、CitationVerifier、TemplateGuide。

规则：
- 不添加上游没有的新事实或数字。
- 每个外部事实使用 source citation key；每个派生数字使用 metric citation key。
- 清楚区分事实、分析、风险、潜在催化和数据限制。
- 不给出买卖建议、目标价或确定性收益承诺。
- 必须包含数据截止日和“非投资建议”声明。
- 遇到冲突或缺失，写进限制章节，不能静默隐藏。
- 输出必须符合 ReportDraft schema，最终 Markdown 由模板渲染器生成。
```

## 12.4 Phase 3.5 运行时提示词骨架（受控反思与修订闭环）

这些不是在开发时给 Cline 的提示词，而是将来写进 `src/.../prompts/` 的运行时模板
（P03-18 / P03-19 实现）。程序由 schema 注入输入，不能靠自由文本拼接不可信内容。

### 12.4.1 writer_revision_prompt_v1（P03-18）

```text
角色：你是负责定向修订的研究报告编辑。
目标：只修复 RevisionRequest.issues 指出的问题，生成修订版 ReportDraft。
唯一可用的输入：
- 原始 research_pack（ResearchPack）
- 原始 analysis_pack（FinancialAnalysisPack）
- 本次 RevisionRequest（issues / revision_number / original_draft_version）

规则：
- 只能修改被 QualityIssue 指出的章节/表述/免责声明问题；
- 不得新增上游不存在的事实或数字；
- 不得修改 FinancialFact 与 MetricResult 的任何值；
- 必须保留已有且仍有效的引用（citation_keys）；
- 证据不足时不猜测：删除无法支撑的结论，或在报告中列为"证据不足"；
- 若无法完成定向修订，明确返回"无法修订"（交由 Flow 路由到 REJECT）。

禁止：添加新来源、修改原始数字、引入买卖建议/目标价、删除"非投资建议"声明。
```

### 12.4.2 research_supplement_prompt_v1（P03-19）

```text
角色：你是按需补证的公开信息研究员。
目标：只搜集 SupplementResearchRequest.missing_evidence 指定的证据，产出结构化补充来源。
不允许：
- 重做全部研究；
- 写出财务分析结论（那是 Analysis 的职责）；
- 绕过 as_of_date。

要求：
- 只检索 required_source_type 指定的来源类型（如 sec_filing / web / company_ir）；
- 遵守 as_of_date，只用当日或之前的信息；
- 返回结构化补充来源（标题/URL/发布时间/访问时间）；
- 找不到时如实返回"未找到"，不得编造。
```

## 13. 简历提示词（项目完成后才能用）

```text
请根据 evals/ 下的实际评估报告、效率实验和部署证据撰写 3 条简历 bullet。不得使用没有原始记录支撑的百分比、QPS、成功率、成本或时间。

每条使用“做了什么 + 如何做 + 测量结果 + 业务价值”的结构，突出：
- CrewAI 三 Agent 顺序协作和结构化中间产物；
- typed tools、幂等恢复、重试/降级、质量门禁；
- Docker Compose、PostgreSQL、Redis、Prometheus/Grafana/OpenTelemetry 的本地完整部署；
- 成功率和人工效率的真实数据。

如果某项没有测量结果，请写成“设计并实现”，不要编造 XX%。
```

## 14. 常见坏提示词与改法

| 坏提示词 | 问题 | 改法 |
|---|---|---|
| “帮我把整个项目写完” | 范围无限，难验证、难学习 | 指定一个任务 ID 和停止条件 |
| “写得生产级一点” | 没有可验收含义 | 明确超时、错误分类、测试和指标 |
| “尽量别出错” | 无法测试 | 列错误矩阵、重试上限和失败状态 |
| “给我算财务指标” | LLM 可能心算/编数 | 要求调用确定性计算工具并记录输入 |
| “用最新技术栈” | 容易追新和不兼容 | 要求查官方兼容性、锁版本并写 ADR |
| “测试一下” | 可能只口头说通过 | 给出必须执行的命令并要求粘贴真实结果摘要 |
| “顺便优化其他代码” | 引发 scope creep | 明确只改任务必需文件、下一任务只建议 |
