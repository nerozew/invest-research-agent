## 1. 什么是缓存（Cache）

**一句话**：缓存是一层"更快、临时"的存储，里面放着某些数据的**副本**，目的是避免每次都要重新去"慢的地方"取。

生活类比：

- 做饭常用调料放**灶台边的架子**上，而不是每次都去楼下超市买。架子 = 缓存，超市 = 数据源。
- 常看的文件放**桌面**，而不是每次从服务器下载。桌面 = 缓存，服务器 = 数据源。

关键认知：**缓存不是"另一份数据"，而是"同一份数据放在离你更近、读起来更快的地方"。**

计算机里的"缓存金字塔"（越往上越快、越小、越贵）：

```
CPU 寄存器     （纳秒级，几个 KB）
   ↓
L1 / L2 / L3   （CPU 内置缓存，几十 KB ~ 几十 MB）
   ↓
内存 RAM       （微秒级，GB 级）
   ↓
磁盘 / SSD     （毫秒级）
   ↓
网络 / 数据库   （毫秒~秒级，最慢）
```

**每一层都是下一层的缓存**。内存是磁盘的缓存，磁盘是数据库的缓存。你"查缓存"就是问：更快的那层里有没有？有就快，没有就去慢的源头取，取回来再存进缓存。

## 2. 缓存到底怎么存数据？—— 缓存就是一张"字典（key-value）"

这是最关键的一节。很多人以为"缓存是一块内存地址"——**这是错的**。缓存不是一个地址，而是一张 **键值表（key-value / 字典 / 哈希表）**。

### 2.1 字典是什么

字典（dict / hash map）是一个数据结构：**用"名字"快速找到"值"**。

```python
# 这就是一张字典
store = {
    "苹果": 5,       # 键 -> 值
    "香蕉": 3,
    "牛奶": 2,
}
store["香蕉"]        # 取：用键找到值 -> 3
store["面包"] = 1    # 存：把"面包"这个键和值 1 放进去
```

- **键（key）**：给数据起的"名字"，唯一标识。
- **值（value）**：数据本身。
- 底层用**哈希表**实现，查找平均 O(1)（常数时间）——不管表里有多少条，都几乎一样快。

**字典和"地址"的区别**：地址是"内存里的第几格"（`0x7f9a...`），是一种底层定位；字典是"我叫什么名字、里面有什么"。你操作缓存时说的是名字（键），不是地址。地址只是哈希表内部实现时用的细节。

### 2.2 缓存怎么用字典存数据

缓存的本质：**把"计算结果"按"一个能唯一标识它的键"存起来，下次用同样的键来取。**

```
存：cache.put(key, value)      # key 决定"我存的是哪一份数据"
取：cache.get(key)             # 用同一个 key 把数据拿回来
```

**储物柜类比**：一排储物柜，每个柜子有标签（键），里面放东西（值）。你要存东西 → 找一个标签、放进去；要取 → 按标签找柜子。缓存就是这一排柜子，字典就是"标签 → 柜子"的对照表。

### 2.3 本项目里活生生的例子：`ToolCallCache`

```python
class ToolCallCache:
    def __init__(self) -> None:
        self._store: dict[str, Any] = {}    # 就是一个字典！

    def key(self, tool_name: str, params: dict) -> str:
        return f"{tool_name}:{json.dumps(params, sort_keys=True)}"  # 生成键

    def put(self, key: str, value: Any) -> None:
        self._store[key] = value            # 存：往字典里放

    def get(self, key: str) -> Any | None:
        return self._store.get(key)         # 取：按键拿
```

键 = `工具名 + 规范化参数`，例如 `sec_company_facts:{"cik":"1045810","as_of_date":"2025-10-31"}`。
值 = 那次工具调用的成功结果。

所以"数据存在缓存里" = **在字典里，以某个键为名，放了一份结果的副本**。仅此而已。

### 2.4 Redis 也是一张字典

Redis 就是**一张很大的、放在远程服务器上的字典**，用网络读写：

```
SET job:123 "正在运行"     # 存（redis 的 put）
GET job:123                # 取（redis 的 get）
```

区别只是：ToolCallCache 是本进程内存、Job 结束就没了；Redis 是独立服务、跨进程共享、可持久化。

## 3. 为什么要缓存（缓存的作用）

| 作用 | 解释 | 例子（本项目） |
|---|---|---|
| **快** | 命中缓存是微秒级，重算/重取是秒级 | research agent 命中 ToolCallCache 免去一轮 SEC 网络请求 |
| **省** | 昂贵的 API/DB 调用按次计费或限量 | SEC API 有限流（max_rpm），重复调用会触发限流、烧钱 |
| **抗压** | 保护下游，避免被海量请求打爆 | prefetch 把 SEC 查询合并、去重，避免同一 URL 抓两遍 |
| **稳** | 结果固定、可复现 | 同一工具+参数永远返回同一缓存结果 → 报告可复现 |

## 4. 缓存放哪里（缓存的位置）

1. **进程内缓存（in-process）**：在当前服务内存里。最快，但**每个进程各一份**，进程重启就丢。
   → 本项目的 `ToolCallCache`。
2. **本地磁盘缓存**：落在文件里。慢于内存，但重启还在。
3. **远程缓存服务**：独立服务器（Redis / Memcached），**跨进程、跨服务共享**。

## 5. 什么是"缓存池"（Cache Pool）

两种含义：

### 含义 A：缓存条目的"池子"
一个缓存服务里存的大量 key-value 的集合。`job:123`、`idempotency:abc` 这些键就是"池"里的成员。

### 含义 B：连接池（Connection Pool）
到数据库/缓存的 **TCP 连接复用池**。每次建连接很贵，所以预先建一批放着反复用。`socket_connect_timeout` 这类配置就是连接池/客户端层面的。

> "连接池"为什么存在？—— 见下一节的计算机网络补课。

## 6. 计算机网络补课：TCP / UDP / HTTP 和数据库连接

（对理解"连接池"和"为什么数据库连接是 TCP 连接"很有用。）

### 6.1 网络分层（先纠正一个常见误解）

网络协议分**层**，各层各管一段。常用的五层模型：

```
应用层   HTTP、FTP、DNS、PostgreSQL 协议、MySQL 协议   ← 程序之间说的话
  ↓
传输层   TCP、UDP                                     ← 提供"端到端"传输
  ↓
网络层   IP、ICMP                                     ← 负责"寻址、路由"（找到主机）
  ↓
数据链路层 以太网、Wi-Fi                              ← 相邻设备之间的传输
  ↓
物理层   网线、光纤、无线电波                          ← 真正的比特流
```

**关键纠正**：
- **TCP / UDP 是"传输层"（第 4 层），不是网络层。** 网络层是 **IP**。
- **HTTP 是应用层。**
- 常见误解就是把 TCP 当成"网络层"。正确说法：`HTTP（应用层）跑在 TCP（传输层）上，TCP 跑在 IP（网络层）上`。

### 6.2 数据怎么在层与层之间流动（封装/解包）

发一条 HTTP 请求时，数据逐层"套娃"：

```
应用层：  "GET /  HTTP/1.1"              ← 你的数据
传输层：  包上 TCP 头（源端口、目的端口、序号…）   → 变成一个 TCP 段
网络层：  再包上 IP 头（源 IP、目的 IP…）          → 变成一个 IP 包
链路层：  再包上以太网头（源 MAC、目的 MAC…）      → 变成一帧，发出去
```

接收方从下往上**解包**，最后把"GET /"交还给应用。

### 6.3 什么叫"端到端"

- **TCP 是面向连接的、可靠的"端到端"传输**：先三次握手建立连接，然后保证字节不丢、不乱、不重复地到达对方进程。这里的"端"是"主机上的进程"，所以叫端到端。
- **UDP 是无连接的、尽力而为**：不握手、不保证到达，但快。

所以"端到端的连接"就是指 **TCP 连接**——TCP 协议本身就是干这个的。

### 6.4 数据库连接跟 TCP 有什么关系

**数据库连接 = 一个到数据库服务器的 TCP 连接 + 一个数据库自己的协议（应用层）跑在上面。**

- PostgreSQL 监听端口 5432、MySQL 监听 3306，它们都是**用 TCP 传输**的。
- 数据库协议（PostgreSQL wire protocol / MySQL protocol）和 HTTP 一样是**应用层协议**，只不过 HTTP 是"浏览器→网页服务器"的话术，数据库协议是"应用→数据库"的话术。
- 它们都建立在 TCP 之上：连接数据库 = 先 TCP 握手建连接，再按数据库协议说话。

### 6.5 为什么要有连接池

因为**建立/关闭 TCP 连接很贵**：
- 建立要三次握手（SYN → SYN-ACK → ACK），加密场景还要 TLS 握手（来回好几趟）；
- 高频场景下"每查一次就新建一个连接"会白白消耗大量时间。

连接池 = 预先建好一批连接放在池子里，用的时候拿一条、用完还回去，**复用而不是重建**。所以后端配置里会有 `连接池大小`、`空闲超时`、`socket_connect_timeout` 这些——它们管的是这批 TCP 连接怎么维护。

## 7. 缓存的"一生"与后端为什么都要配置缓存

缓存条目的生命周期，配置就是管理这几件事：

| 配置点 | 问题 | 常见答案 |
|---|---|---|
| **TTL（过期时间）** | 数据多久失效？ | 5 分钟 / 1 小时 / 永久 |
| **淘汰策略** | 满了踢谁？ | LRU（最久未用）/ LFU（最少使用）/ FIFO |
| **写策略** | 先写缓存还是先写库？ | write-through / write-back / write-around |
| **失效方式** | 数据变了怎么通知缓存？ | 主动删 key / TTL 到期 / 版本号 |
| **一致性** | 缓存和数据库对不上怎么办？ | 缓存最大的坑 |

后端讲究缓存配置，本质是权衡**性能 / 成本 / 一致性**三角：
- 缓存设太短 → 经常打底库，慢、贵；
- 设太长 → 数据陈旧；
- 不处理下面的三个经典问题 → 一个异常请求就能打挂数据库。

### 7.1 TTL（存活时间）和"过期"到底是什么意思

**TTL = Time To Live，存活时间。** 就是给每个缓存条目设定的"有效期"。

- 写入缓存时，带上一个 TTL，比如 `SET key value EX 300`（Redis 写法：300 秒后过期）。
- **"过期" = 这个条目的有效期到了**。过期后，这个 key 在缓存里视为"不存在"。
- 用户来查一个**已过期**的 key → 缓存 miss → 去慢的源头重新取 → 取回来再以新的 TTL 写进缓存。
- 所以"过期"不是数据被删除那一下，而是"这段缓存不再算数了，该重新取一份了"。

**为什么要 TTL（为什么不永久缓存）？** 因为底层数据**会变**。
- 用户改了个性签名，缓存的旧签名不能一直用 → 需要过期，让下次重新拉。
- 不设 TTL 的代价 = 永远是旧数据（数据陈旧）；TTL 太短的代价 = 频繁打底库（慢、贵）。所以"配置缓存"很大程度就是**选一个合适的 TTL**。

> 本项目 `ToolCallCache` **故意不设 TTL**：它只活一个 Job 的时长，Job 结束整个缓存销毁，底层数据在这个 Job 内也不会变，所以不需要过期机制。

## 8. 缓存三大经典问题 + 热点 key（详细版）

这三个问题都是"**缓存没命中时，请求压到下面那层（DB/源），把源打崩**"的变体。

### 8.1 缓存穿透（Penetration）—— 查"不存在的东西"

- **场景**：请求查一个 key，它**既不在缓存，也不在数据库**（比如恶意扫一个不存在的 ID）。
- **发生了什么**：每次请求缓存 miss → 打到数据库 miss → 返回空。数据库被"根本没意义"的查询反复轰炸。
- **为什么叫穿透**：请求"穿透"了缓存层，直接扎到数据库。
- **解决**：① 空结果也缓存（缓存一个"空"值）；② 布隆过滤器先挡一层"这个 key 肯定不存在"。

### 8.2 缓存击穿（Breakdown）—— 热点 key 过期的瞬间

- **场景**：有一个**超热门 key**（比如"顶流商品详情"），大量请求都靠它。
- **发生了什么**：这个 key 恰好在缓存里**过期了**。过期的瞬间，所有本来命中缓存的请求**同时** miss，一起打到数据库 → 数据库瞬间被压垮。
- **为什么叫击穿**：单个热点 key 的"防线"被击穿。
- **解决**：① 互斥锁——只让一个请求去重建缓存，其它请求等它；② 热点 key 不设过期，改为后台定时刷新。

### 8.3 缓存雪崩（Avalanche）—— 一大批 key 同时过期

- **场景**：很多 key 用了**相同的 TTL**，在同一时刻一起过期（或缓存服务整体重启）。
- **发生了什么**：一大波本来靠缓存的请求**同时** miss，全部压到数据库 → 数据库被打崩。
- **解决**：① TTL 加**随机抖动**（每个 key 的过期时间错开）；② 多级缓存（本地 + 远程）；③ 缓存服务高可用。

### 8.4 热点 key（Hot Key）—— 单个 key 流量异常大

- 单个 key 被超高频率访问。问题不只在于它过期时的"击穿"，还在于**单点压力**（所有流量都打这一个键，即使缓存命中，这个键所在的服务/节点也很累）。
- **解决**：热点 key 多副本（同一数据存多个 key 分散压力）、本地缓存兜底、限流。

### 8.5 本项目适用吗？

`ToolCallCache` 是 **per-Job、无 TTL、Job 结束即销毁** 的简单 memoization 缓存：
- **没有 TTL** → 击穿/雪崩这两个"过期"问题**基本不适用**；
- **per-Job 不共享** → 不存在"跨任务热点 key"；
- 它主要解决的是 **去重 + 免重复网络**（对应"省钱/抗压"），不是分布式缓存那套。

Redis 在本项目主要当 **Celery 任务队列 + 探活**，也不涉及这些缓存击穿问题。

## 9. 本项目里到底有哪些"缓存"，各干什么

### 9.1 `ToolCallCache` —— 真正的数据缓存（进程内、per-Job）

位置：`src/invest_research/infrastructure/tool_cache.py`

- **在哪**：每个 Job 一个实例，存在运行该 Job 的进程内存里。
- **键**：`工具名 + 规范化参数`。
- **谁写**：**prefetch** 并行跑完工具后写成功结果。
- **谁读**：research agent 的工具包装（real_tools）先 `has()/get()`，命中就直接返回，不发网络请求。
- **作用**：去重 + 加速 + 省钱。prefetch 预热，agent 命中，互不重复。
- **特性**：线程安全；只缓存成功结果（失败不缓存，允许重试）。

### 9.2 Redis —— 主要不是"数据缓存"，而是队列 + 探活

配置：`src/invest_research/settings.py` 的 `redis_url` / `broker_url`。

| 用途 | 在哪 | 干什么 |
|---|---|---|
| **Celery broker（消息队列）** | `queue/celery_app.py`、`wiring.py` | 把任务投递给 Worker。这是 Redis 最主要的作用——**队列** |
| **/readiness 探活** | `api/health.py` | `redis_client.ping()` 检查可用性 |
| ~~幂等~~ | —— | 幂等在 **PostgreSQL**（`idempotency_keys` 表），不在 Redis |

> 幂等为什么放 PostgreSQL 而不是 Redis？因为幂等记录要**持久、强一致、可审计**——Redis 的持久化/一致性不如数据库稳妥。

### 9.3 其它"缓存类"东西

- 数据库索引（数据库内部的加速结构）；
- ArtifactStore 工件（结果落盘，是持久化产物，不是易失缓存）；
- 浏览器/CDN 缓存（前端层面）。

## 10. 用一个完整例子串起来（NVDA 研究报告）

```
用户提交 NVDA 研究任务
  → Worker 从 Redis 队列取到任务
  → prefetch 并行调 SEC submissions / Company Facts / Google 搜索
      → 每个工具结果写入 ToolCallCache（key=工具名+参数）
  → research agent 组装 ResearchPack
      → 它带的工具先查 ToolCallCache：
          命中 → 直接用（不重复打 SEC）
          未命中 → 才真实调用（受预算+缓存约束）
  → 后续 analysis / writer / 质检 / 发布
```

**没有缓存**：research agent 可能对同一 SEC URL 调两遍（浪费 + 限流），结果不可复现，每次都全量重抓。
**有了 ToolCallCache**：同一 Job 内"同一工具+同一参数"只执行一次，其余命中缓存。

## 11. 一句话总结

> **缓存 = 一张"键→值"的字典，把慢/贵/反复取的结果按名字存一份副本，换速度、省成本、扛压力。**
> 缓存不是一块裸地址，而是命名槽位（key → value）。后端讲究缓存配置，是因为一致性、过期、淘汰、穿透/击穿/雪崩任何一个没处理好，都会从"优化"变成"事故源"。
> 本项目里：**ToolCallCache**（内存字典）是真缓存，**Redis** 主要是 Celery 队列，别把两者混为一谈。
