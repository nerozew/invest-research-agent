## 第一部分：网络 —— 端口、端到端、HTTP 应用层

### 1.1 TCP/UDP 的"端到端"到底指什么

TCP 报文的头部有**源端口**和**目的端口**，网络层 IP 头有**源 IP**和**目的 IP**。一个"通信端点"其实是 **IP + 端口** 的组合：

```
通信的"端" = (IP 地址, 端口号)
             ↑ 找到哪台主机    ↑ 找到主机上哪个进程/服务
```

所以 TCP 的"端到端" = **一个 (IP:端口) 到另一个 (IP:端口)**：
- 传输层管"主机上的哪个进程在通信"（端口）；
- 网络层管"哪两台主机之间通信"（IP）。

你之前问"端到端是不是端口到端口"——**对了一半**。准确说是"主机到主机（IP）+ 进程到进程（端口）"。端口的作用是：一台服务器上同时跑着 HTTP 服务（80）、数据库（5432）、SSH（22），**靠端口区分是发给哪个服务的**。

### 1.2 "不同的网页，端口不一样" —— 这是误解

**所有网页用的端口基本都是 80（HTTP）或 443（HTTPS），同一个。**

那不同网页怎么区分？靠**应用层**，不靠端口：

- HTTP 请求里有 `Host` 头（`Host: www.aaa.com`）和**路径**（`/news`、`/about`）。
- 服务器收到请求后，根据 Host + 路径决定返回哪个页面。
- 一台服务器只占一个 443 端口，却能同时服务几百个网站（叫**虚拟主机**）。

结论：**端口区分"服务"，Host/路径区分"页面/内容"**。两者不是一个维度。

### 1.3 同一个软件、同一个端口，怎么跟不同人聊天？—— 靠应用层

你打开一个聊天软件，跟 A、B、C 不同的人聊天、发不同消息——**都是同一个软件、连的同一个服务器端口（如 443）**，不是每个人一个端口。区分靠两层：

1. **连接层**：你每次建立 TCP 连接，客户端会用一个**随机的源端口**（比如 52000）。服务器端看到的是 `(你的IP, 52000)` → `(服务器IP, 443)`。**每条 TCP 连接是可区分的**。
2. **应用层**：同一连接里可能有多条消息，靠**应用协议**把它们分帧、区分——HTTP 是"请求/响应"配对，聊天协议/WebSocket 是"一帧一帧消息"。消息里还带 `to: A`、`to: B`、会话 ID 这样的字段，**由应用自己判断这条消息属于和谁的对话**。

所以你的理解基本正确：**端口不变，不同消息是 HTTP/应用协议在"分拣"**。端口只管"送到这个软件/服务"，至于消息给谁，是应用层的事。

## 第二部分：数据库 —— 为什么慢、索引是什么、怎么优化

### 2.1 为什么数据库查询"慢"

数据库通常存在**磁盘**上（或远程另一台机器）。慢的根源：

| 层 | 速度 | 对比 |
|---|---|---|
| 内存（缓存） | 微秒级 | 快 ~1000 倍 |
| 磁盘（SSD/HDD） | 毫秒级 | 慢 |
| 网络往返（远程 DB） | 还要加网络延迟 | 更慢 |

另外，**没有索引的查询要做"全表扫描"**：把表里每一行都读一遍、逐个比较条件。表越大越慢。这是"查询慢"的最大原因。

> 所以才有缓存：缓存是"内存层"，DB 是"磁盘层"。命中缓存跳过 DB，就是跳过最慢的那层。

### 2.2 用一张表讲清楚"索引是什么"

假设一张用户表：

```
users
| id | name   | age | email          |
|----|--------|-----|----------------|
| 1  | Alice  | 25  | alice@x.com    |
| 2  | Bob    | 30  | bob@x.com      |
| 3  | Carol  | 22  | carol@x.com    |
| ...| ...    | ... | ...            |
| 1000000 | ... | ... | ...         |   ← 100 万行
```

**没有索引**，执行 `SELECT * FROM users WHERE name = 'Alice'`：

1. 从第 1 行开始，把每一行的 `name` 拿出来和 `'Alice'` 比较；
2. 一直比到第 100 万行才结束。
→ **全表扫描，O(N)，100 万行比较 100 万次**。这就是慢。

**有索引**，先建：`CREATE INDEX idx_name ON users(name);`

索引的本质 = **给某一列额外建一棵"排序查找树"（B+ 树）**，像书的目录：

```
索引 idx_name（按 name 排序的一棵 B+ 树）
    B树查找 "Alice" → O(log N)，几步就到
    叶子节点存着"这条记录在表里的位置（主键 id=1）"
```

执行同一查询：
1. 走索引树，按 name 二分查找，"Alice" 几步就找到了（O(log N)）；
2. 从树的叶子拿到对应的行位置，去取整行。
→ 100 万行里找一条，从"比 100 万次"降到"十几步"。

**一句话**：索引 = 数据库为"经常用来查的列"建的目录/排序树，让查找从"逐行翻"变成"按目录翻"。

### 2.3 MySQL（InnoDB）单表的查询过程

MySQL 默认引擎 InnoDB 里，表和索引的关系：

- **主键（primary key）索引 = 聚簇索引（clustered index）**：表的数据行本身就按主键组织成一棵 B+ 树，叶子就是整行数据。主键查 = 一步到叶子拿整行。
- **普通索引（二级索引）**：单独一棵 B+ 树，叶子存的是**主键值**（不是整行）。
  - 用二级索引查，流程是：**先查二级索引树 → 拿到主键 → 再回聚簇索引树取整行**。这个"回去取整行"叫**回表**，多一次 I/O。
  - 如果查询只需要 `name` 和 `id`（索引里都有），就不回表 → 叫**覆盖索引**。

```
SELECT * FROM users WHERE name='Alice'
  ① 二级索引 idx_name 树：找 name='Alice' → 拿到主键 id=1
  ② 回表：用 id=1 去聚簇索引树 → 取整行 → 返回
```

### 2.4 为什么索引能快、什么情况反而没用

**为什么快**：B+ 树把"逐行线性比较"（O(N)）变成"按排序二分查找"（O(log N)）。而且索引本身常驻内存（InnoDB 的 buffer pool 会缓存索引页），比直接读磁盘表快得多。

**什么情况索引没用（白建）**：
- 在索引列上用了**函数**：`WHERE UPPER(name)='ALICE'` → 无法用排序好的树，只能全扫。
- **前导模糊**：`WHERE name LIKE '%lice'` → 不知道从哪个字母开始，全扫。（`LIKE 'Ali%'` 可以用索引。）
- **选择性太差**：`WHERE gender='male'`，一半数据都一样 → 用索引还不如全扫，优化器会放弃索引。
- `SELECT *` 却只靠二级索引且要很多列 → 大量回表，可能反而不如全扫。

### 2.5 让单表查询更快的实用优化

| 优化 | 做法 | 原理 |
|---|---|---|
| **建索引** | 给 `WHERE` / `ORDER BY` / `GROUP BY` 的列建索引 | 查找变 O(log N) |
| **覆盖索引** | 查询列都放进索引（`SELECT name, id` 而不是 `SELECT *`） | 免回表 |
| **复合索引** | 多条件按"最左前缀"建 `(a, b)` 索引 | 一次树查找满足多条件 |
| **避免函数/前导模糊** | 别在索引列上套函数；`'Ali%'` 而不是 `'%li%'` | 保持能用索引 |
| **用 EXPLAIN 看执行计划** | `EXPLAIN SELECT ...`，看有没有走索引、有没有回表 | 让数据库告诉你它怎么查 |
| **控制数据量/加缓存** | 该归档的归档；高频结果用缓存挡在前面 | 减少打到 DB 的量 |

### 2.6 回到你的问题：为什么"不能让数据直接查数据库"

不是"不能"，而是**代价高**：
- DB 在磁盘/远程，慢；
- 没索引就是全表扫描，更慢；
- 高并发下所有请求都打 DB，DB 会成为瓶颈甚至被打崩。

所以架构上习惯在 DB 前面加**缓存**：**热数据走缓存（内存，快），缓存没命中才落 DB（磁盘，慢）**。缓存就是"数据库的缓冲区"，挡掉绝大部分重复查询。这就是 docs/27 里 `ToolCallCache` 存在的意义。

### 2.7 B+ 树详解：数据到底怎么按索引排、搜索怎么走

（前面说"索引是一棵 B+ 树"——这节把 B+ 树本身讲透。）

#### 2.7.1 先忘掉 B+ 这个名词——它就是一棵"加宽了的二叉搜索树（BST）"

你懂 BST：每个节点 **1 个键、2 个孩子**，左 < 键 < 右，查的时候比大小往下走。

```
BST 节点：        50              ← 1 个键，分出 2 个区间
                /    \
              <50     >50
```

B+ 树把同一套"比大小往下走"的规则**原封不动**，只是**一个节点装多个键**：

```
B+ 节点：     [ 30 | 50 | 70 ]     ← 3 个键，分出 4 个区间
              /   |   |   \
            <30  30~50  50~70  >70
```

规则和 BST 一模一样：查一个数，跟节点里的键逐个比大小，决定走哪个孩子。只是把多个"BST 节点"并排塞进一个节点（**扇出大**，孩子可以几百上千）。

一棵真实的 B+ 树（用分数举例）：

```
             [ 60 | 90 ]                ← 内部节点：3 个孩子区间 <60 / 60~90 / >90
           /      |       \
     [20|40|50]  [70|80]   [95|99|100]  ← 叶子：装全部数据，且按顺序用链表串
```

**搜索 80**：根 `[60|90]`，80 在 60~90 之间 → 走中间孩子 → 叶子 `[70|80]` 找到 80。2 层 = 2 步。
**搜索 30**：根 `[60|90]`，30 < 60 → 走左边 → 叶子 `[20|40|50]` 找到 30。也是 2 步。

**和 BST 的根本区别只有两条：**

1. **一个节点装很多键 → 树特别矮**：
   - 100 万条，BST（二叉）要 log₂(100万) ≈ **20 层**；
   - B+ 树（一个节点 1000 键）只要 log₁₀₀₀(100万) = **2 层**。
   - 数据库读一次磁盘 = 读一页（16KB）= 一个节点，**层数就是磁盘读次数**：20 次 vs 2 次。

2. **数据全部只在叶子，且叶子用链表串起来**（B+ 的 "+" 就是指这个）：
   - 内部节点只放"路标"键（不放数据）→ 能塞更多键 → 树更矮；
   - 叶子按顺序装全部数据 + 链表相连 → **范围查询**（`BETWEEN 3 AND 8`）找到起点顺着链表扫。

> 注意：**B 不是 Binary（二叉）**，是 **Balanced**（自平衡，不会退化成链）。所以 B+ 树 ≠ 二叉树。

#### 2.7.2 为什么数据库选 B+ 树（不是数组 / 二叉树 / 哈希）

| 结构 | 点查 | 范围查/排序 | 插入删除 | 为什么数据库不只用它 |
|---|---|---|---|---|
| 有序数组 | O(log N) | ✅ 好 | ❌ O(N) 要挪元素 | 插入/删除太慢 |
| 二叉搜索树 | O(log N) | ✅ | ⚠️ 可能退化成链 O(N) | 会不平衡 |
| 哈希索引 | O(1) | ❌ 无法范围/排序 | ✅ | 只能精确匹配 |
| **B+ 树** | O(log N) | ✅ 走叶子链表 | ✅ O(log N) | —— 全都要 |

而且数据库读写以"**页**"为单位（InnoDB 默认 16KB），B+ 树每个节点 ≈ 一页，**每层一次磁盘 I/O**。

#### 2.7.3 InnoDB 里数据到底怎么"排"

InnoDB 是**索引组织表**：**整张表本身就是一个 B+ 树**。

- **聚簇索引（主键索引）= 表本身**：叶子节点就是**整行数据**，按主键排序。你建了主键，表就按主键排成一棵 B+ 树。
- **二级索引（普通索引）**：另建一棵 B+ 树，叶子存的是**主键值**（不是整行）。

```
聚簇索引（主键）:  id → [整行数据]      ← 数据就存在这里
二级索引 (name):  name → id             ← 只有名字和对应的主键
```

所以"按索引排列" = 数据库按你建的每个索引列，各自维护一棵有序的 B+ 树。

#### 2.7.4 一次搜索怎么走

**主键点查** `WHERE id = 5`：
```
聚簇索引树：根 → 按 id 比较 → 逐层往下 → 到叶子直接拿整行
```

**二级索引点查** `WHERE name = 'Alice'`（name 有索引）：
```
① 二级索引树：找 'Alice' → 拿到主键 id=1
② 回表：用 id=1 去聚簇索引树 → 拿整行
```

**范围查** `WHERE id BETWEEN 3 AND 8`：
```
① 聚簇索引先找到叶子 3
② 顺着叶子的链表一路扫到 8    ← 链表让范围查询很便宜
```

**为什么快 = 磁盘 I/O 少**：全表扫描要读 N 页；B+ 树只要读"高度"这么多页（3~4 页），而且这些页常驻内存（InnoDB buffer pool）。

#### 2.7.5 把几个概念串起来

- **回表**：走二级索引拿到主键后，还要再回聚簇索引取整行 = 多一次树查找（多一次 I/O）。
- **覆盖索引**：查询要的列全部包含在二级索引里 → 不用回表。例如索引是 `(name, age)`，查询 `SELECT name, age FROM users WHERE name='Alice'` → 免回表。
- **复合索引 / 最左前缀**：索引 `(a, b, c)` 能服务 `a`、`a,b`、`a,b,c` 的查询；但 `WHERE b=...` 单独用不上它。所以建复合索引要把"最常当第一个条件的列"放最左。
- **索引什么时候白建**：见 2.4（列上套函数、前导模糊 `%xxx`、选择性太差、大量回表）。

#### 2.7.6 一张表总结

| 概念 | 一句话 |
|---|---|
| **B+ 树** | 多叉、自平衡、叶子存全部数据并用链表串联的查找树 |
| **扇出** | 一个节点孩子的数量；越大树越矮、越少磁盘 I/O |
| **高度** | 查一次要下几层 ≈ 磁盘 I/O 次数；百万级约 3~4 层 |
| **聚簇索引** | 主键索引；叶子 = 整行；表本身就是它 |
| **二级索引** | 普通索引；叶子 = 主键值；查完整行要回表 |
| **回表** | 二级索引 → 拿主键 → 回聚簇索引取整行 |
| **覆盖索引** | 查询列都在索引里 → 免回表 |
| **复合索引** | 多列索引，按最左前缀使用 |
| **为什么快** | 点查 O(log N)、范围查走叶子链表、磁盘 I/O 只有树高那么几次 |

#### 2.7.7 为什么普通 BST 会退化成链表，B+ 树不会

**一句话**：BST 没有"最低填充"约束，B+ 树有（每个节点键数必须 ∈ [半满, 满]），并且靠**分裂/合并**强制维持。

**BST 为什么退化**：普通 BST 只保证"左 < 根 < 右"，不保证平衡。按顺序插 1,2,3,4,5：

```
插 1 →  1
插 2 →  1 → 2（2 挂到 1 右边）
插 3 →  1 → 2 → 3（3 挂到 2 右边）
插 5 →  … 一路往右挂
```

结果成一条链 `1→2→3→4→5`，查找 5 要 5 步 = O(N)。没有 AVL/红黑树的旋转兜底就会这样。

**B+ 树为什么不会**：节点满了就**分裂**（一半留在原节点、一半分到新节点、中间键上提）。仍按顺序插 1..5（假设一个节点最多 3 键）：

```
插 1,2,3 →  [1,2,3]
插 4 →  [1,2,3] 满 → 分裂成 [1,2] 和 [3,4]，把 3 上提
        → 根 [3]，叶子 [1,2]、[3,4]
插 5 →  [3,4] 满 → 分裂成 [3] 和 [4,5]，把 4 上提
        → 根 [3,4]，叶子 [1,2]、[3]、[4,5]
```

结果还是 2 层树，**没有变成链**。三个原因：

1. **叶子永远同一层**：B+ 树只在"根也满了"时分裂根、整体长高一层（所有叶子同时下沉）。所以永远完美平衡。
2. **分裂保证节点不太空**：分裂后每个节点至少半满，不会出现"一个键一个孩子"排成一串。
3. **平衡是结构自带**：BST 的平衡靠"事后旋转补救"，B+ 的平衡靠"分裂这个结构机制"——所以数据库绝不允许查询偶发退化成 O(N)。

代价：节点可能半空（多占空间），但换来深度恒定 O(log N)、磁盘读次数恒定少。

## 一句话总结

> **端口**区分"服务"，**Host/路径/应用协议**区分"页面/消息"——同一个端口可以承载无数不同的内容。
> **数据库慢**主要是因为磁盘 I/O 和全表扫描；**索引**就是给常用列建的"目录（B+ 树）"，把 O(N) 全扫变成 O(log N) 查找；**优化**就是建对索引、避免回表、别让索引失效、再用 EXPLAIN 验证。
